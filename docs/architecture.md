# 架构说明

LoRwright 用截图、规则和 ADB 输入推进英雄之路。`core/` 负责自主闭环，CLI 提供启动、观测和控制；Agent 在开发期补充程序能力。Jinx 和 Elise 各自完整自动冒险是验收目标，当前覆盖及证据见 [`status.md`](status.md)。

## 运行边界

| 部分 | 职责 | 主要位置 |
|---|---|---|
| 设备 | 截图、点击、事件级拖拽、应用启动 | `core/device/` |
| 感知 | 将截图转为 UI、手牌、单位、数值与可信度信息 | `core/perceive/` |
| 决策 | 根据当前状态产生语义 `Action`，可弃权 | `core/decide/` |
| 英雄包 | 牌表、专属识别、打法及奖励偏好 | `core/champions/` |
| 执行 | 语义动作转为设计坐标、手势计划 | `core/act/` |
| 流程 | 冒险推进、战斗循环、动作后验、等待与停止 | `core/loop/` |
| 会话 | 运行身份、事件、心跳、设备锁与协作停止 | `core/runtime/` |
| CLI | 装配核心，提供前台和后台命令 | `cli/app.py`、`cli/sessions.py` |

`core/runtime/` 不识别画面、不决定打法。CLI 启动后，核心自行推进已支持步骤，无需 Agent 每动作批准或调度。GUI 待整体能力稳定后复用同一核心，本阶段不增加 GUI 或网络服务。

运行时采用 [ADR-0004](adr/0004-pure-script-decision.md) 的纯脚本决策。历史 JEV/LLM 层已移除；旧设计完整保存在 [历史快照](history/architecture-before-control-loop-20261115.md)，不作为当前架构。

## 自主闭环

冒险外层 `AdventureLoop` 识别主页、地图、节点、奖励和结算等已支持场景；战斗交给 `Engine`，战斗结束后再回外层处理。未覆盖的页面会保留证据并停止，不能据此声称完整冒险已实现。

战斗执行顺序是：

1. 获取新鲜帧并构造 `GameState`；保留缺失读数和未识别身份，不将未知伪装为正常值。
2. 若有未完成动作，先观察预期结果或确认步骤；等待期间不重复发出同一输入。
3. 路由英雄规则及通用策略，选择语义动作；按动作所需信息和当前 UI 检查能否执行。
4. `Translator` 生成 `ClickPlan`，执行前再次检查帧时效；执行层将设计坐标换为设备像素。
5. 单独核验输入后的可见变化，确认后再更新策略进度并继续；结果未知到期则存图停止。

手牌展开会改变卡位，因此展开与拖牌分帧处理。攻击/格挡声明与确认也分阶段核验。输入命令成功、可见变化、战斗结束、奖励到账和冒险完成是不同事实。

## 策略弃权与等待

`Router` 顺序采用首个非 `None` 的动作。英雄专属规则由 CLI 装配到策略链，通用规则处理出单位、攻击、格挡、确认等可复用行为；奖励排序是独立决策能力，由冒险流程调用。

- `None`：本策略没有适用动作，后续策略继续判断。
- `NO_OP`：当前确需等待，本轮不再继续后续策略。
- 全部策略弃权：只在确认 `MY_TURN_IDLE` 时允许结束回合，其他状态保持无输入；收起手牌检查场面等流程可先拦截该兜底。

英雄或组合优先表达排序偏好，不表示必须凑齐才能继续。缺少某张牌、无法识别火箭或未知牌存在时，应让不依赖该信息的已知出牌、攻击等行为继续。允许放弃部分收益，避免理想打法无限阻塞普通动作。

## 局部未知与停止边界

以下行为已在本地实现并通过离线回归，尚待 f1 实机验收，见 [`handoff.md`](handoff.md)。过期普通法力在决策视图中标为 `-1`，过期法术法力为 `None`，原始观测保留供诊断；0 费动作不需要法力读数，付费出牌仍需当前支付证据。

| 未知内容 | 处理边界 |
|---|---|
| 部分手牌身份/效果 | 跳过无依据的候选，保留其他可证明动作；不要求所有新卡逐张建档 |
| 法力或血量读数 | 仅限制依赖该读数的动作；支付能力须有依据，攻击/确认等动作按自身前提检查 |
| 目标、弃牌或其他交互 | 只执行已识别且有依据的交互；不凭费用或位置猜未知效果 |
| UI 未知、帧过期、持续缺少动作前提、持续无动作、持续等待对方 | 核心按单调时钟有界观察；期限到达保存截图，报告原因并停止 |
| 输入已发出但预期结果未知 | 在动作期限内核验；超时停止，不重放旧计划 |

当前未知单位的通用视觉依据仅覆盖有限卡框/蓝光等场景，不代表任意新卡或附加费用均已理解。弃牌目前仍是单次选择、采样截图后停止，完整确认与转场未实现闭环。

`Watchdog` 与 `RecoveryPolicy` 提供卡住检测及恢复选择，但“重试/重开/重启”枚举不等于这些动作都有安全可执行路径。无法确认重试依据时停止；客户端重启默认受配置限制。系统并非所有异常都可自动恢复，心跳正常或画面变化也不证明游戏业务有进展。

## 数据与坐标

`GameState` 保存识别到的 UI、手牌、单位、攻击令牌和读数有效性；`Action` 表达语义意图；`ClickPlan` 保存执行坐标/手势。决策不直接截图或操作设备，英雄知识留在英雄包。

战斗截图按 `config.screen`（当前 1920×1080）归一化，执行时反算设备坐标。地图导航主要以原生 1920×1080 验证，不能将战斗的缩放支持推广成完整冒险的多分辨率保证。模板与语言、缩放、动画和遮挡相关，现有样本覆盖不等于所有画面可靠。

运行模板在 `assets/`，当前回归截图在 `tests/fixtures/`，历史证据在 `research/archives/` 等归档目录。研究结论用于设计参考，不替代本项目代码验证或实机验收。MAA/MaaFramework 的证据与适用限制见 [研究笔记](research/maa-maaframework-control-loop.md)。

## 观测与控制

会话报告阶段、策略、动作、等待截止、输入结果、最后进展与截图引用。CLI 查询持久化状态与事件，不承担游戏策略或逐动作推进；协作停止在输入安全点生效。具体命令、字段与退出码以 [`cli.md`](cli.md) 为准。
