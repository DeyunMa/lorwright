# 架构说明

LoRwright 用截图、规则和 ADB 输入推进英雄之路。`core/` 负责自主闭环，CLI 提供启动、观测和控制；Agent 在开发期补充程序能力。Jinx 和 Elise 各自完整自动冒险是验收目标，当前覆盖及证据见 [`status.md`](status.md)。

## 运行边界

| 部分 | 职责 | 主要位置 |
|---|---|---|
| 设备 | 截图、点击、事件级拖拽、应用启动 | `core/device/` |
| 感知 | 将截图转为 UI、手牌、单位、数值与可信度信息 | `core/perceive/` |
| 决策 | 根据当前状态产生语义 `Action`，可弃权 | `core/decide/` |
| 英雄包 | 牌表、专属识别、打法及奖励偏好 | `core/champions/` |
| 执行 | 语义动作转为设计坐标、手势计划 | `core/act/` |
| 流程 | 冒险推进、战斗循环、动作后验、等待与停止 | `core/loop/` |
| 会话 | 运行身份、事件、心跳、设备锁与协作停止 | `core/runtime/` |
| CLI | 装配核心，提供前台和后台命令 | `cli/app.py`、`cli/sessions.py` |

`core/runtime/` 不识别画面、不决定打法。CLI 启动后，核心自行推进已支持步骤，无需 Agent 每动作批准或调度。GUI 待整体能力稳定后复用同一核心，本阶段不增加 GUI 或网络服务。

运行时采用 [ADR-0004](adr/0004-pure-script-decision.md) 的纯脚本决策。历史 JEV/LLM 层已移除；旧设计完整保存在 [历史快照](history/architecture-before-control-loop-20261115.md)，不作为当前架构。

## 自主闭环

程序按三层循环组合能力。下层完成后将结果交给上层，由上层核验并决定何时继续。

| 循环 | 负责的步骤 | 当前落点 |
|---|---|---|
| 单场战斗 | 把换牌、出牌、攻击、格挡、确认等原子能力组合起来，推进到战斗结束。 | `Engine` |
| 单次冒险 | 在地图上移向节点，处理节点事件、战斗、选牌与其他奖励，核验最终结算。遇到战斗时调用战斗循环，战斗结束后接着推进当前冒险。 | `AdventureLoop` 覆盖已支持场景，未覆盖的页面保留证据并停止。 |
| 跨冒险任务 | 按任务选择或切换冒险，按需切换英雄和地图。核验上一场结果并重置场次状态，再启动下一次冒险。每周冒险、每月挑战等任务都复用下两层。 | 目标设计。已有单场入口和周常选择能力，完整的跨冒险调度及切换仍待实现与验收。 |

各层的实际覆盖与实机证据见[阶段状态](status.md)。

挑战次数：每月挑战有次数限制，历史记录为每位英雄每月 3 次，具体数值待复核；其他冒险不限次数，失败后可直接重新挑战（2026-11-19 用户确认）。

地图的一跳导航由 `perceive/mapnav.py` 的 `reachable_nodes(image, hero=...)` 提供：形状检测先产生圆节点、菱形及展示框，头像仅作当前位置锚点；随后统一核验当前节点、同一亮线连通域及连续边，最后排除目标锁定、完成、暗态和遮挡。头像遮挡只按射线与头像的实际几何交集处理，不按节点业务或路线方向切换算法。菱形本体和所属展示框可以提供不同连接端口，但只返回一个真实点击目标；仅见展示框时返回 `needs_reveal`，平移后必须用新帧确认真实节点。

`node_kind` 在可达性成立后提供业务语义，冒险层再按优先级选路；语义图标未知不使已核实的边失效。省略 `hero` 的画面中心推断仅保留给历史诊断；运行时装配头像识别器后，头像拒识必须停止。当前仍只支持已验证的青色/蓝白亮线及 1920×1080 地图，不代表全局规划或任意地图外观均已覆盖。

战斗执行顺序是：

1. 获取新鲜帧并构造 `GameState`；保留缺失读数和未识别身份，不将未知伪装为正常值。
2. 若有未完成动作，先观察预期结果或确认步骤；等待期间不重复发出同一输入。
3. 路由英雄规则及通用策略，选择语义动作；按动作所需信息和当前 UI 检查能否执行。
4. `Translator` 生成 `ClickPlan`，执行前再次检查帧时效；执行层将设计坐标换为设备像素。
5. 单独核验输入后的可见变化，确认后再更新策略进度并继续；结果未知到期则存图停止。

`ActionReadiness` 在战斗输入前比较连续两张新鲜帧中的相关证据：所选卡槽、目标、单位、换牌状态或确认提示；位置允许 12px 抖动。无关未知牌、血量或资源不统一阻塞动作。过期帧及实际输入清空连续证据，下一帧重新路由，不缓存旧候选。首次不稳定开始的准备期限固定为 `loop.action_timeout_s`，UI 或候选变化不刷新截止。策略生成候选不能推进执行状态：Elise 通过 `on_action_sent` 记录已发送拖牌，通用格挡通过成功的 `on_action_outcome` 才进入确认。

手牌展开会改变卡位，因此展开后用新帧定位，再发出拖牌手势。ADB 出牌依赖「按住 → 停顿 → 拖 → 松手」的事件级输入。攻击/格挡声明与确认也分阶段核验。展开等待若遇到明确的 `COMBAT_RESOLVING` 和 `action_confirm` / `action_commit`，返回 `NEEDS_INPUT` 交给现有确认策略；这时尚未拖牌，不更新出牌进度或暂存原出牌。未知动画继续受原期限约束。

主动攻击或结束回合前，展开手牌可能遮挡单位；已有收手机制会先核验手牌收起，再用新帧重新路由和取单位坐标。输入命令成功、可见变化、战斗结束、奖励到账和冒险完成是不同事实。各项实机覆盖及本地待部署变更见 [`status.md`](status.md)。

待确认出牌保留同一个 `ActionOutcome`，包含原始状态、英雄专属预期和截止。附加确认的观察窗口不得超过父动作截止；确认成功只完成确认交互，原出牌继续用后续新帧核验，未知结果到期统一停止，不重复拖牌。确认与原出牌分别记录 `action_outcome` 并各自只通知一次成功。换牌确认、独立战斗确认和结束回合采用至少 20 秒的阶段窗口，覆盖入场或结算动画；该窗口仍固定截止，不能为父出牌续期。

结算无文字背景须同时匹配两个独立区域，且在待核验动作的原截止前取得新鲜证据，才可交接到一次最多 60 秒的只读观察。背景不证明结束，也不通知动作成功；原动作截止不变，返回战斗继续按原记录核验。UNKNOWN、过期帧及重复背景不延长阶段期限，到期存图停止。本能力目前只覆盖已采样外观及 Engine；冒险奖励/继续操作沿用自身有界后继核验。

`readings.my_units_visible / enemy_units_visible` 记录本帧检出数量的下界；零检出、未配置或未知 UI 不产生确认空场的读数，也不沿用上一帧。结束回合后，同一已知 UI 和手牌视图下的新鲜敌军检出数量增加可交回 Router；该交接只表示有新信息可重新决策，不证明完整场面或上次结束回合已成功。行动资格、集合完整性等其余 T1 工作仍待实现。


## 策略弃权与等待

`Router` 顺序采用首个非 `None` 的动作。英雄专属规则由 CLI 装配到策略链，通用规则处理出单位、攻击、格挡、确认等可复用行为；奖励排序是独立决策能力，由冒险流程调用。

- `None`：本策略没有适用动作，后续策略继续判断。
- `NO_OP`：当前确需等待，本轮不再继续后续策略。
- 全部策略弃权：只在确认 `MY_TURN_IDLE` 时允许结束回合，其他状态保持无输入；收起手牌检查场面等流程可先拦截该兜底。

英雄或组合优先表达排序偏好，不表示必须凑齐才能继续。缺少某张牌、无法识别火箭或未知牌存在时，应让不依赖该信息的已知出牌、攻击等行为继续。允许放弃部分收益，避免理想打法无限阻塞普通动作。

当前这一组合语义在战斗 Router 中明确，其他消费者还未完全统一：默认 `PlayUnitPolicy` 排在 `HeroFirstPolicy` 前，卡牌奖励则按是否有专属 hook 选择实现，尚未区分专属规则不适用与证据不足。`ChampionPack` 的声明也少于实际使用的视觉/奖励 hook。已确认问题与按 loop 装配的改造拆票见 [统一能力审计](research/capability-loop-audit-20261116.md)，实施由 [总 issue #17](https://github.com/DeyunMa/lorwright/issues/17) 跟踪。

## 卡牌类型与选牌

游戏中的牌分为单位、法术、地标和装备。卡牌和道具各有独立的品质，识别或排序涉及品质时应使用对应对象的品质。已核验的视觉示例见[冒险素材说明](../assets/adventure/README.md)。

| 类型 | 规则与当前处理 |
|---|---|
| 单位 | 分英雄与侍从。卡面左下为力量，右下为血量。两种单位都进入 Jinx 奖励的优先组。 |
| 法术 | 有慢速、快速、疾速等结算速度。当前仍由已知卡牌的规则处理，奖励识别只输出法术类型。 |
| 地标 | 占一个场上位置，带主动效果的地标可点击发动。当前跳过已识别的地标奖励，不主动打出或发动已识别的地标。仅凭现有单位检测无法核验完整场面占用。 |
| 装备 | 需要指定友方单位，并赋予该单位装备效果。自动出装备等到友方目标流程可核验后再启用。 |

Jinx 选奖励时先排除地标。有可辨认的单位就只比较单位，同组内先选已核验的最低费用，同费再选品质更高的卡。费用无法比较时弃权。同费时品质未知的候选排在已知品质之后。卡牌底部的徽记独立于附带道具，绿色优秀对应 `common`，蓝色稀有对应 `rare`，紫色史诗对应 `epic`。牌名可以保持未知。

## 能力品质与选择

品质名称以游戏显示的文字为准。能力品质由高到低依次为传说（橙色，`legendary`）、史诗（紫色，`epic`）、稀有（蓝色，`rare`）、优秀（绿色，`common`）。能力的画面识别要求品质文字与颜色一致。

- 免费能力奖励先匹配英雄专属偏好。无匹配时优先选择最高品质。
- 占星家等付费能力事件先筛出余额可负担的选项，再按品质从高到低选择。同品质优先选便宜的，不重抽。

## 局部未知与停止边界

读数要求随动作决定。过期普通法力在决策视图中标为 `-1`，过期法术法力为 `None`，原始观测保留供诊断；0 费动作不需要法力读数，付费出牌仍需当前支付证据。攻击、格挡或确认按各自动作前提检查，不统一等待全部法力/血量可读。实现与实机范围分别记录在 [`status.md`](status.md)。

| 未知内容 | 处理边界 |
|---|---|
| 部分手牌身份/效果 | 跳过无依据的候选，保留其他可证明动作；不要求所有新卡逐张建档 |
| 牌名未知但牌型可确认 | 用户确认（2026-11-21）：识别不出牌名不阻止出牌。先识别手牌牌型；能确认是单位（展开态卡面左下有力量、右下有血量），且法力足够、有有效拖拽点，就按 `PlayUnitPolicy` 的顺序（费用低者优先）打出，不要求在牌表中。非单位或牌型不确定的未知牌仍跳过，不猜效果。手牌扇形间距窄时也要能识别牌型。实拍展开扇形里力量/血量角标常在屏幕外或被邻牌遮住；用户确认（同日）可加卡框/法术标记作牌型证据：法术费用徽章下的星形法术标记、法术圆形卡框与单位方形卡框的区别。确认是单位才出，确认不了仍跳过 |
| 法力或血量读数 | 仅限制依赖该读数的动作；支付能力须有依据，攻击/确认等动作按自身前提检查 |
| 目标、弃牌或其他交互 | 只执行已识别且有依据的交互；不凭费用或位置猜未知效果 |
| UI 未知、帧过期、持续缺少动作前提、持续无动作、持续等待对方 | 核心按单调时钟有界观察；期限到达保存截图，报告原因并停止 |
| 输入已发出但预期结果未知 | 在动作期限内核验；超时停止，不重放旧计划 |

当前未知单位的通用视觉依据仅覆盖有限卡框/蓝光等场景，不代表任意新卡或附加费用均已理解。弃牌目前仍是单次选择、采样截图后停止，完整确认与转场未实现闭环。

冒险点击和平移发出前核对当前采集帧的时效。过期时保存画面并停止，原坐标失效。多个后继页面的轮询按各自的单调时钟截止执行。截图在截止后返回时，程序记录耗时并将该帧用于诊断。发生重连也沿用原有转场截止，超时后需要从新会话重新观察当前页面。

`Watchdog` 与 `RecoveryPolicy` 提供卡住检测及恢复选择，但“重试/重开/重启”枚举不等于这些动作都有安全可执行路径。无法确认重试依据时停止；客户端重启默认受配置限制。系统并非所有异常都可自动恢复，心跳正常或画面变化也不证明游戏业务有进展。

## 数据与坐标

`GameState` 保存识别到的 UI、手牌、单位、攻击令牌和读数有效性；`Action` 表达语义意图；`ClickPlan` 保存执行坐标/手势。决策不直接截图或操作设备，英雄知识留在英雄包。

战斗截图按 `config.screen`（当前 1920×1080）归一化，执行时反算设备坐标。法力和主堡血量来自布局中的固定屏幕区域；场上单位的数值框相对卡片固定，卡片会随站位和声明行移动。单位定位先使用橙色攻击底；普通色板满足形状判据时直接提供候选，异常色块则由字形中心恢复成对数值框，核验左右底色及数字后才接受。数字读取复用已有字形模板，生命支持白/绿/红数字，无法核实的数值保留未知。

Jinx 手牌身份的 ORB 匹配不仅检查分数，还检查卡面到本牌费用徽章的几何归属，避免同一裁剪内的相邻卡面借名。模板关键点和特殊卡面裁图锚点留在英雄包；身份不足保持未知，不因费用相同或落点可拖而认定卡牌效果。

地图导航主要以原生 1920×1080 验证，不能将战斗的缩放支持推广成完整冒险的多分辨率保证。模板与语言、缩放、动画和遮挡相关；成对数值框覆盖当前实拍，不代表任意卡框、光效或数字均可靠。

运行模板在 `assets/` 和英雄包。回归和历史图片位于库外测试数据目录，案例标注和来源说明随仓维护。目录说明见[项目目录与图片](layout.md)。MAA/MaaFramework 的设计参考见[研究笔记](research/maa-maaframework-control-loop.md)。

## 开发闭环

程序自主运行冒险，CLI 提供会话状态、事件、日志和停止截图。Agent 根据这些证据定位卡点、补齐能力并验证修复。人按需补充游戏机制、确定开发优先级和验收标准，并参与需要授权的实机操作。人的参与发生在开发和验收过程中，游戏内动作仍由程序决策和执行。

1. 从 [CLI 状态与事件](cli.md#agent-推荐流程)取得阶段、停止原因和截图，找出缺失的识别、决策、交互或结果核验能力。
2. 用失败素材复现卡点。优先修复可跨场次复用的能力，将英雄或任务确有的差异放到对应策略或配置。已有多场素材时，按[多冒险截图对照](offline-validation.md#多冒险截图对照)复验原失败场次和其他已有覆盖的相关场次。
3. 完成本地回归后，在获准的实机运行中继续观察后继和结果。把新的稳定游戏规则补到对应文档，将影响验收结论的结果按证据层次更新到[阶段状态](status.md)，供下一轮迭代使用。

## 观测与控制

会话报告阶段、策略、动作、等待截止、输入结果、最后进展与截图引用。CLI 查询持久化状态与事件，不承担游戏策略或逐动作推进；协作停止在输入安全点生效。具体命令、字段与退出码以 [`cli.md`](cli.md) 为准。
