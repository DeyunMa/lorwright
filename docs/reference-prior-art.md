# 参考前作：MAA 与 ALAS

两个已经跑了多年的同类项目，架构上验证过的做法直接拿来用，避免重新踩坑。

| 项目 | 形态 | 规模 |
|---|---|---|
| **MAA**（MaaAssistantArknights） | C++ 核心 + 多前端（WPF/CLI/…） | 明日方舟，社区最大 |
| **ALAS**（AzurLaneAutoScript） | 纯 Python + Web 控制台 | 碧蓝航线 |

> ⚠️ **只学设计，不抄代码。** MAA 是 AGPL-3.0，ALAS 是 GPL-3.0；
> 复制代码会让 lorwright 也被传染成强著佐权协议，与"可能闭源售卖"冲突。
> 这里记录的是**架构模式**，实现自己写。

---

## 一、MAA 的四个可借鉴点

### 1. 三层分离：任务 / 视觉 / 控制

```
任务编排（做什么）
   ↓
视觉识别（看到了什么）
   ↓
控制器（怎么操作）
```

lorwright 对应：`decide/` → `perceive/` → `device/`。
**这个分层我们已经在用，且与 MAA 同构**——说明方向是对的。

### 2. 任务（task）是一串带识别的步骤，不是一次点击

MAA 的每个任务 = `[识别 → 动作 → 识别 → 动作 …]`，每步失败可重试。
lorwright 现在是**动作级**（一个 tick 一个动作），粒度太细：

| | MAA | lorwright 现状 |
|---|---|---|
| 重试单位 | 任务（如「刷一关」） | 单个动作 |
| 失败处理 | 重试当前任务 N 次 | `RecoveryPolicy` 分 4 级 |
| 状态 | 任务内的步骤索引 | 无 |

**改进方向**：引入 `Task` 概念（`打一局周本` = 进图 → 选人 → 打完 → 领奖），
`RecoveryPolicy` 挂在任务上而不是 tick 上。见 issue #6。

### 3. 「作业」= 配置驱动的策略插件

MAA 的 copilot JSON 描述「这一关谁放哪、什么时候开技能」，社区可共享。
这正是 ADR-0001 里 `Policy` 插件想做的事——**别人写策略，不用改代码**。

**启示**：`Policy` 的输入输出要能序列化成 JSON（state → action），
这样策略可以存在文件里、可以分享、可以版本化。

### 4. 资源版本化

MAA 的模板图和任务配置带版本号，游戏更新后只替换资源，不动代码。

**启示**：`assets/` 要有版本标记（对应游戏版本 `live_7-10-13`）。
换分辨率 / 游戏更新时，能明确知道"模板过期了"，而不是默默匹配失败。

## 二、ALAS 的四个可借鉴点

### 1. 纯 Python，没有编译产物

和 lorwright 一致。好处：改一行就能跑，不用等编译。

### 2. Web 控制台，不是桌面 GUI

ALAS 用浏览器看状态、改配置、启停任务。比 WPF/Qt 轻得多。

**启示**：将来要做界面，优先 **FastAPI + 单页 HTML**，不要 Electron/Qt。
（ADR-0001 里 GUI 是延后项，这个决定不变，只是提前定方向。）

### 3. 任务调度器

ALAS 有"每天几点跑什么"的调度。lorwright 暂时不需要（手动跑），
但多开 + 24×7 之后会需要。**先记着，不现在做。**

### 4. 配置持久化与多实例

ALAS 支持多开，每个实例一份配置。

**启示**：`config/settings.yaml` 要能按实例拆分
（`settings-emulator-5554.yaml`），或者支持 `--config` 参数。

## 四、学不了的部分

| MAA/ALAS 的做法 | 为什么学不了 |
|---|---|
| 「简单决策」：刷固定关卡，路线固定 | 英雄之路是策略对局，每回合局面不同 |
| 大量固定坐标点击 | LoR 手牌是扇形、位置随牌数变 |
| 靠 UI 控件树定位 | LoR 用 SurfaceView 渲染，`uiautomator dump` 拿不到内部控件 |
| 单一模板匹配 | 需要颜色探针 + 卡牌识别 + 规则决策组合 |

**这正是 lorwright 的难点所在**：MAA 解决"重复劳动"，我们要解决"重复决策"。

## 六、一句话总结

**MAA 教我们「任务怎么组织、资源怎么版本化」，ALAS 教我们「界面怎么轻、多开怎么管」。
两者都没解决「局面怎么决策」——那才是 lorwright 自己的东西。**
